Tracking breaks quietly, and a dashboard cannot tell you

Analytics instrumentation is code, but it is the only code with no failure mode. A missing event does not throw. A misnamed event does not fail a build. Nothing goes red. Your app keeps working, events keep arriving, and the numbers are quietly wrong for months.

It shows up in two shapes. Coverage gaps: a screen ships, the event is forgotten, and nobody notices until someone asks a question the data cannot answer. Naming drift: two event names grow around one action, so every funnel, retention curve and conversion rate built on either one is short, in a way that still looks perfectly reasonable.

Both are invisible in a product analytics tool, because anything downstream of your code can only report what your code actually sent. Tracking you forgot is undetectable there by definition. That is why the check belongs where the events are written, next to the code and in review, rather than in a tracking plan spreadsheet that drifts a little further from reality with every release.

Four of them, written out the way they surface in review. The examples below use invented event names, not anybody's real product.

The last screen before payment is presented to users and has zero analytics: no screen view, no interaction events. You cannot see how often people reach it, or how many turn back at it.

Proposed change

Send a screen view when it appears, so the step becomes visible in the funnel.

Rename Two events cover one action: cart_add and cart_added errornaming/duplicate-concept

Both are live and both are still sending. Any count of items added to the cart is short unless the query unions the pair, and nothing about either name says which one the current code uses.

two call sites, two different names, same moment

Proposed change

Keep the one current code sends, treat the other as historical, and note the cutover date for anyone querying across it.

Rename signup_prompt is a thing, not an action warningnaming/verb

Sibling events use a past-tense verb, so this one sorts and reads apart from the rest. Small on its own, and the reason a taxonomy stops being predictable once a few of them pile up.

Proposed change

Rename so the last part is an action, matching the events around it.

Fix properties order_completed carries payment_method on only some events warningproperties/call-site-drift

One code path passes the full order, another does not, so the same event name arrives in two different shapes. Any breakdown by payment method silently drops the events that came from the second path.

two call sites, one passes the order object, one does not

Proposed change

Send the same properties from every call site, so one event name means one contract.

Questions

What is analytics instrumentation?

The code in your app that sends analytics events: the calls, the event names they use, and the properties they attach. It sits between what a user does and what your product analytics tool records. Developers write it, which is exactly why it drifts from whatever plan the rest of the team believes exists.

What is an event taxonomy, or a tracking plan?

The set of event names your product sends, plus the rules behind them. A good one is predictable enough that two developers pick the same name for the same kind of action without asking each other, and descriptive detail lives in event properties rather than multiplying into new event names. Most teams keep this in a spreadsheet, which is where the drift starts.

Why do event names become inconsistent?

Because nothing checks them. Every developer picks a verb, and add, create, new and save all end up meaning the same thing. No build fails. The names accumulate release after release until two of them cover one action, and every count built on either one is short.

How do you find screens with missing tracking?

Not in a dashboard. A dashboard only shows what was sent, so tracking you forgot is invisible there by definition. The only way to find it is to compare the screens that exist in your code against the events your code actually sends.
